# Workbench Jobs To Be Done

This document is the canonical ergonomics reference for Workbench. Each job names the complete steady-state command sequence a user runs to get it done. The sequences below are a product contract, not documentation of incidental behavior: if completing a job requires more commands, more flags, or more prior knowledge than written here, that is a defect. Docs, the CLI help, the authored `workbench` skill, and the web UX must stay consistent with this file.

How to read each job: "steady state" is what a returning user types after one-time setup is done. One-time setup is listed separately and may include login, the first publish, or the first hosted run depending on the job. Every command sequence assumes manifest defaults from `.workbench/agents.yaml` and the optional `.workbench/versions.yaml`; selector flags exist only to intentionally broaden or narrow the matrix. Every accepted `run`, `grade`, `eval`, `improve`, or `retry` launch creates one durable run; selected version, agent, case, sample, execution, and grading detail lives in jobs and `workbench.run.v1` measurements rather than in several sibling run ids. The contract grammar lives in [`../SPEC.md`](../SPEC.md); the operator guide is [`cli.md`](cli.md).

Live validation uses the Workbench device login against the shared test account `test@test.com` with password `Test123!Test`. That account proves Workbench Cloud auth only; it does not include Codex or Claude provider OAuth credentials and does not by itself prove hosted compute, because real hosted eval/improve runs require an organization-owned Cloud skill whose organization has an active Team or Enterprise plan. In headless shells, `workbench login --no-open --json` starts the device flow and prints the same bounded resume command as `workbench login --start-only --no-open --json`; open the JSON `verificationUriComplete`, sign in with the shared test account, approve the device request, then run the printed `workbench login --wait --timeout 120 --json` command. Disposable publish checks in the shared `test` namespace must use a unique first-publish handle such as `workbench publish --as test/earnings-prep-$(date +%s) --private`; handle conflicts are expected and the printed remediation is authoritative. Hosted auto-link and publish create persistent Cloud skill projects, so throwaway validation should use disposable names and can clean them with `workbench delete test/NAME --dry-run` followed by `workbench delete test/NAME --yes`. Provider-backed validation uses OAuth only, never API keys: generate missing Codex auth with `codex login --device-auth`, then capture it with `workbench login codex --method oauth`; when Codex native auth already exists, Workbench setup guidance skips directly to `workbench login codex --method oauth`. Captured provider OAuth must be enough for provider-backed execution and nested rubric judges; successful grading must not require `OPENAI_API_KEY` or another provider API-key environment fallback. Empty or malformed Codex `auth.json` files are treated as missing native auth for readiness and rejected by `workbench login codex --method oauth` with `provider_oauth_invalid`. For Claude, run `claude setup-token` in an interactive shell when native Claude OAuth material is missing, complete browser authorization, copy the OAuth token it prints, then capture it with `CLAUDE_CODE_OAUTH_TOKEN=... workbench login claude --method oauth`. Validators can pass `--profile-root DIR` for isolated provider capture; `DIR` is an alternate home root where Codex reads `DIR/.codex/auth.json` and Claude reads `DIR/.claude.json` plus the exported `CLAUDE_CODE_OAUTH_TOKEN`. Once Workbench provider auth is captured, native provider files in the current `HOME` are not required for Workbench runs. `workbench logout PROVIDER` removes Workbench's captured provider auth but intentionally leaves native provider CLI auth alone; when no captured provider record exists, it still reports the local adapter as disconnected and writes no auth-store marker. JSON `remoteAdapterAuth.status` describes the remote provider connection after cleanup and `remoteAdapterAuth.workbenchCloud.status` describes whether Workbench Cloud auth was available. Remove native auth separately when a clean-room validation pass requires it. Validators must still verify Workbench's missing-token guidance from a throwaway `HOME`. Full provider-backed success requires real provider OAuth, full hosted success requires an active organization plan, and provider-independent clean-room validation can use `--agent local` or `command` agents.

## Job 1: Get my expertise into a skill others can run

Create a skill, validate it against representative cases, and make it installable for a team or the public.

    workbench new earnings-prep
    cd earnings-prep
    # edit SKILL.md and .workbench/cases/
    workbench eval
    workbench publish

One-time setup: `workbench login` once per machine for Cloud publish, plus provider auth for the scaffolded default Codex agent: `codex login --device-auth` if `~/.codex/auth.json` is missing, then `workbench login codex --method oauth`. If native Codex auth already exists, readiness and setup output begin at the Workbench capture command. If provider auth is captured before Cloud login, the successful bare `workbench login` uploads the connected provider bundle to Cloud automatically. Teams that want Claude as the default use `claude setup-token` when needed, then `CLAUDE_CODE_OAUTH_TOKEN=... workbench login claude --method oauth`, then configure the default agent. The first `publish` derives the `OWNER/SKILL` handle from the logged-in namespace and project folder, links the Cloud skill project, records the selected source version in the published-version set, moves the current publication pointer, leaves Cloud sync status clean for immediate `status` and `sync cloud --dry-run` checks, and defaults to `--private`. `workbench publish --as OWNER/SKILL` is the one-time override when the derived handle is wrong, and later bare `publish` uses the persisted handle. Steady state after that is bare `workbench publish` with zero flags, like bare `git push` after `git push -u`; if the same version, handle, and audience are already current published source, it returns `Already published` and the same install command. `publish --dry-run` makes no changes: its `next` is the exact real publish command to retry, while the install handoff appears separately as JSON `installCommand` and human `after publish:` because that command is useful only after a real publish. Audience changes only when an audience flag is provided: `--private`, `--team` (organization members), or `--public` (anyone, including the public `skills` CLI through well-known discovery). `--team` requires an organization-owned skill and errors use team visibility wording rather than storage enum names. A later bare `publish` preserves the last explicit audience. `publish` exposes two read surfaces from the same source version: an installable agent skill package for `workbench install`, and editable Workbench source for `workbench clone OWNER/SKILL[@VERSION]|URL DIR`; the taught handoff still uses the handle form. It ends by printing the exact `workbench install OWNER/SKILL` line to hand to people who only need to use the skill. Prior published versions remain addressable as `OWNER/SKILL@VERSION` until the owner runs `workbench unpublish VERSION`; `VERSION` may be the full version id or any unambiguous displayed prefix, and the current published version must be replaced by publishing another version before it can be unpublished. Current-version unpublish errors point to `workbench publish VERSION` for a concrete still-published replacement when one is available, otherwise to `workbench versions`. `unpublish --dry-run` validates that the target is a removable prior version, reports the current published version, and prints `workbench unpublish VERSION` as the follow-up without deleting source availability; non-dry-run `unpublish` validates the same state before printing destructive removal progress. `workbench delete OWNER/SKILL --dry-run` previews deletion of the entire Cloud skill project, and `workbench delete OWNER/SKILL --yes` removes the project, published source, install package, hosted runs, and synced objects. No URLs are ever typed in the taught happy path and the words "remote" and "sync" do not appear in this job.

Sharing is the handoff after publish, not a separate lifecycle command. To share with teammates inside an organization, publish with team visibility and send the handle command for the recipient's job:

    workbench publish --team
    workbench install acme/earnings-prep
    workbench clone acme/earnings-prep earnings-prep

The install command is for teammates who only need to use the skill in their agent. The clone command is for teammates who need editable Workbench source, evals, and future improvements. To pin the handoff to a vetted version, send `acme/earnings-prep@VERSION` in the install or clone source.

To share publicly, publish with public visibility and send the same handle command. Public sharing also makes the skill visible through public well-known discovery:

    workbench publish --public
    workbench install test/workbench-smoke
    workbench clone test/workbench-smoke smoke

The public handle remains the product-facing identifier; full Cloud URLs are copy-paste conveniences, not the taught sharing path.

## Job 2: Use a skill someone else made

    workbench install test/workbench-smoke
    workbench skills

The maintained public validation fixture is `test/workbench-smoke`; real handoffs use the publisher's `OWNER/SKILL` handle. The `OWNER/SKILL` handle is the universal identifier for published skills. Full Cloud URLs are accepted by `install` and `clone` when pasted from a browser but are never required. Private and team skills use the same handle with Workbench Cloud auth.

`workbench install OWNER/SKILL` is strictly mutating and requires a source argument. The bare handle installs the current published version; `workbench install OWNER/SKILL@VERSION` installs an exact still-published version. With no flags, it installs the agent skill package for the current coding agent in the current folder. If the current coding agent cannot be detected, it fails with one command-shaped remediation such as `workbench install OWNER/SKILL --target codex`. `--target codex|claude` selects one coding-agent product, and `--scope folder|global` selects where it is written. Installing for both Codex and Claude is two explicit commands. The install target paths are implementation details, but the package directory uses the handle's `SKILL` segment so publish, install, and clone share the same handoff name. Re-running the same install command over an unchanged Workbench-managed copy is idempotent and does not rewrite files or advance install metadata timestamps; changed or unmanaged destination content requires `--yes`. Overwrite remediation preserves the source pin, scope, directory, and any explicit target flag from the attempted command, but omits target flags that were only inferred from the current coding agent. `install --dry-run` still writes nothing and reports that same overwrite as blocked with the exact `--yes` command in `next` rather than presenting it as an ordinary plan; blocked dry-runs exit nonzero and JSON sets `ok: false` while preserving the install target details.

Installed skill roots contain only the agent skill package: `SKILL.md`, scripts, references, assets, and package support files. `workbench install` never writes `.workbench/eval.yaml`, `.workbench/cases`, runtime objects, refs, logs, remotes, locks, or install metadata inside the package directory. This keeps "use this skill in my agent" separate from "work on this skill as a Workbench project."

`workbench skills` is the inventory command. With no flags, it scans configured Codex and Claude folder and global skill roots visible from the current directory; it also reports the current editable Workbench project itself when run from a folder containing `SKILL.md` and `.workbench` controls. It does not search arbitrary sibling folders. Empty human inventory output says this directly and points arbitrary sibling `SKILL.md` work toward `cd` plus `workbench init` or shell search. `--target codex|claude` narrows to one coding-agent product, `--scope folder|global` narrows to one access scope, and `--dir DIR` changes the folder-scope root. Broad inventory sorts folder rows before global rows, managed/current or Workbench-project rows before unmanaged rows, and the detected current coding agent before other targets, so the skill you just installed or are standing in is not buried by global skill sprawl. To keep that broad default usable in real homes, unmanaged global rows are omitted unless `--scope global` is requested; managed/current, modified, missing, and Workbench-project global rows remain visible. Inventory is read-only, takes no project lock, performs no network access by default, and shows `current`, `modified`, `missing`, `project`, `unmanaged`, or `duplicate-name` status when it can tell. `project` means the visible local skill folder has Workbench controls but no install-ledger provenance. It does not show a `not installed` universe because catalog search is a separate job. Removal is ordinary filesystem deletion from the visible skills root after checking inventory.

To get editable source and Workbench controls for evaluation or improvement, use `clone`, not `install`:

    workbench clone test/workbench-smoke smoke

`workbench clone OWNER/SKILL[@VERSION]|URL DIR` creates a Workbench project containing the package plus authored `.workbench` controls when the source has them. It does not copy the source project's runtime objects, refs, sync state, logs, locks, remotes, install ledgers, or `.agents` directories, but it does initialize fresh local `.workbench/objects`, `.workbench/refs`, and `.workbench/sync` state for the new project. Seeing those runtime directories after clone means local project state was initialized, not copied from the source. If the source is package-only, it creates the package plus the normal minimal `.workbench` scaffold. `workbench eval` and `workbench improve` operate on that project source; installed global or folder copies do not affect them unless explicitly vendored or referenced in `.workbench/versions.yaml`.

## Job 3: Put workflow evals around an existing local skill

    workbench skills
    cd PATH_TO_EXISTING_SKILL
    workbench init
    # edit .workbench/cases/
    workbench eval

`workbench skills` is the broad, read-only scan that helps find local Codex and Claude skills already visible through their configured folder and global skill roots, plus the current editable Workbench project when you are standing in one. It is not a general filesystem finder for arbitrary local `SKILL.md` directories; empty output carries that hint, and users should use shell search or `cd` directly when the skill lives outside those roots. This is the product-led path from skill sprawl to a measured workflow: scan first, choose one existing high-value skill, then initialize that skill in place. After choosing an existing skill directory, `workbench init` runs in that directory, requires `SKILL.md`, creates `.workbench/eval.yaml`, `.workbench/agents.yaml`, `.workbench/cases/`, and Workbench runtime state, and does not rewrite the package. `init` does not install, publish, clone, evaluate, improve, or generate cases; it only makes the current skill directory Workbench-managed so the normal eval/improve/results/publish loop can begin.

## Job 4: Define the workflow quality bar for this skill

The workflow quality bar is the set of cases, rubrics, expected checks, examples, scores, and review criteria that define whether the skill does the recurring job well. Eval authoring is file editing, not command running — the same way git has no command for writing code. The authored, evaluated, and versioned agent skill package is everything outside `.workbench/**`: `SKILL.md`, scripts, references, assets, package metadata, helper files, and any other package support files. The authored Workbench quality surface that affects skill-source version identity is `.workbench/eval.yaml` (the grade adapter), `.workbench/cases/*/case.yaml` (representative workflow inputs with rubrics or tests), and optional `.workbench/versions.yaml` or `.workbench/environment/`. `.workbench/agents.yaml` is authored runtime configuration and is published/cloned with editable source, but agents are snapshotted as their own result-matrix axis, so changing agent configuration alone does not invalidate current skill results. Runtime `.workbench` directories such as objects, refs, sync, tmp, logs, and locks are not installable package source. A minimal provider-backed case is:

```yaml
version: 1
id: case-001
prompt: Create an earnings prep note for GOOGL.
rubric:
  - Explains the likely investor focus areas.
  - Avoids overclaiming facts not present in the context.
```

Local or command-backed test cases additionally need either a top-level `command` in `case.yaml` or an executable `tests/test.sh` under the case directory; shell tests write their public score to `$OUTPUT_DIR/result.json`. Those shell tests are judgment inputs: `workbench grade` or the grade phase of `workbench eval` runs them against existing execute output, while output-only `workbench run` records runner output and traces without invoking the test harness. The no-case `next:` command is `workbench case draft CASE_ID`, which always creates the draft prompt/rubric file. Local and command-backed projects also get an executable `tests/test.sh` harness and open both files; provider-backed projects create and open only `case.yaml`. Draft placeholders are launch gates: `run` requires the prompt placeholder to be replaced, while `grade` and `eval` also require the rubric placeholder to be replaced before judgment evidence can be recorded. This lets provider-backed eval development run a prompt first, inspect output, then add the rubric before grading. The generated shell harness still intentionally fails with score `0` until edited, so local and command-backed projects do not accidentally record perfect draft evidence. A real no-case eval fails before scheduling; `eval --dry-run` remains a no-write preview and reports `cases=0` together with any non-case launch readiness issues. When reusable evidence already exists, dry-run reports whole eval reuse in `cachedRunIds`, reusable execute-only evidence in `cachedJobIds`, and split run/grade reuse in `cachedJobIds` plus the owning `cachedRunIds`. The best cases often come from observed failures, recent agent conversations, corrections, and review notes: inspect a run with `workbench show RUN_ID`, then write or edit the case files directly. Creating a fresh case is creating a folder, listing is `ls .workbench/cases`, and removing is deleting the folder - safely, because authored source is versioned at every command boundary and recoverable via `switch`.

## Job 5: Develop evals interactively from prompts and judgment

    workbench new ./earnings-prep --agent codex --model gpt-5.4-mini
    cd ./earnings-prep
    codex login --device-auth
    workbench login codex --method oauth
    workbench case draft investor-focus
    # edit .workbench/cases/investor-focus/case.yaml with the prompt
    workbench run --agents default --cases investor-focus
    workbench show RUN_ID
    workbench show EXECUTE_JOB_ID
    # add or edit the rubric in .workbench/cases/investor-focus/case.yaml
    workbench grade --agents default --cases investor-focus
    workbench show GRADE_JOB_ID
    # edit the rubric again
    workbench grade --agents default --cases investor-focus
    workbench grade --agents default --cases investor-focus --rerun
    workbench eval --agents default --cases investor-focus

This is the ad hoc eval-development loop: draft one prompt, run the actual default Codex agent (`gpt-5.4-mini`) against it, inspect the produced answer and runner trace, write or edit the rubric, grade the existing output, inspect the grade trace and rationale, then edit the rubric and regrade until the quality bar matches expert judgment. The native `codex login --device-auth` command is only needed when the local Codex auth file is missing; after native auth exists, setup starts at `workbench login codex --method oauth`.

`workbench run` is allowed after the draft prompt is replaced even if the draft rubric is still a placeholder. `workbench grade` and `workbench eval` refuse that placeholder rubric and point back to the case file, so a prompt-only exploratory run cannot become bogus perfect judgment evidence.

Prompt, public case input, skill-source, agent, or sample changes make execution stale. Rubric, grade adapter, grader config, or private grader-file changes make grading stale only. `workbench grade` never reruns Codex; it selects the latest eligible execute jobs and creates grade jobs for the current grade definition. A repeated `workbench grade` reuses current grade evidence when nothing relevant changed, including failed grade attempts, while `workbench grade --rerun` forces fresh grade jobs only. `workbench eval` is the combined convenience command: it creates missing or stale execute work, then missing or stale grade work, and `workbench eval --rerun` forces both selected phases. If a rubric-only edit follows `workbench run`, `workbench eval` reuses the existing execute job and creates only the missing grade job.

Regrading is side-effect isolated. Each grade job starts from a clean workspace with the subject output, workspace, traces, and result mounted read-only through dependencies, records its own traces and artifacts, and cannot see prior grade job workspace state unless a future explicit evidence-dependency workflow adds that dependency. Inspectability is uniform: `workbench show RUN_ID` explains the whole run, `workbench show EXECUTE_JOB_ID` shows execution output and traces, and `workbench show GRADE_JOB_ID` shows grading result items, rubric rationale, artifacts, and grader trace. The local browser opened by `workbench open` should support the same loop with authored cases, run output, grading, and regrading backed by the same operation and inspection endpoints.

## Job 6: Find out if it clears the workflow quality bar

    workbench eval --dry-run
    workbench run
    workbench grade
    workbench eval
    workbench eval --agents all -n 5
    workbench eval --rerun

`eval --dry-run` previews the selected version, agent, case count, sample count, execute jobs, grade jobs, cached jobs, location, and launch readiness without writing Workbench state. Cloud dry-run uses the same edited-source plan as local dry-run, so a would-create version is previewed in memory instead of requiring a persisted version, but it does not report local `cachedRunIds` as reusable hosted evidence. When provider auth, local Docker sandbox availability, or Workbench Cloud auth is missing, the dry-run still prints the no-write plan and reports blocked readiness with setup remediation instead of scheduling or mutating state; if no cases exist, top-level `next` stays on `workbench case draft CASE_ID`, and the provider or Cloud setup commands remain listed in readiness. Draft prompt placeholders block `run`, `grade`, and `eval`; draft rubric placeholders block `grade` and `eval` but not output-only `run`. Otherwise top-level `next` is one command-shaped first step when one exists, preferring immediate auth/setup commands before hosted plan blockers. Personal hosted-plan blockers explain the organization-owned requirement and preserve the command shape with the documented `ORG/SKILL` placeholder, such as `workbench publish --as ORG/SKILL && workbench eval --cloud`; JSON issues carry the same remediation plus structured requirement details. Real local `run`, `grade`, and `eval` use the same readiness gate before launch: draft placeholders, missing provider auth, unavailable Docker, or an unready grade adapter fails before scheduling, source-version persistence, or run/job/evidence writes.

`workbench run` executes the selected cases only when current execute evidence is missing or stale. It records or reuses execute jobs, runner traces, runner output artifacts, and workspace artifacts, never invokes the grade adapter, and normally ends with `next: workbench grade`; use `workbench run --rerun` when you intentionally want fresh provider output. For local or command scaffolds this can be a simple runner output while `tests/test.sh` evidence appears on the later grade job. `workbench grade` judges existing eligible execution jobs only. It never reruns the skill; each grade job starts from a clean workspace, mounts the subject output, subject workspace, subject traces, and subject result read-only through dependencies, invokes `grade.run`, and records its own traces, artifacts, and generic result items. `workbench eval` combines both phases in one user-started run: it executes any missing or stale selected work, grades any missing or stale selected output, and reuses current execute or grade jobs whenever possible. Scores are projections from grade job result items, not durable fields on runs or jobs. A bad answer is an execute success plus a grade success with a low score, not an execution failure.

Human output prints the run id, compact case/sample/job coverage, per-measurement results, and the score delta against the incumbent version when both sides are scored (for example `earnings-prep v2 0.84 (was 0.79)`), then ends with one command-shaped `next:` suggestion. Below-perfect evidence points to `improve` only when the target agent can improve; otherwise it first teaches `workbench agent add improver ...`, then provider setup for that improver, then the improver rerun after the agent is runnable. The inline delta means `results` is not needed in the daily single-skill loop. `-n` is shorthand for `--samples`. Failed execution after launch is recorded as failed evidence with the error, never as missing data. Failed grading is recorded as failed grade-job evidence and reused by repeated `grade` or cacheable `eval` until `--rerun`; a grade result with score `0` remains a completed judgment.
`--rerun` bypasses cached evidence for the matrix selected by the current command; for `run`, it forces fresh execute jobs, for `grade`, it forces fresh grade jobs, and for `eval`, it forces both selected execute and grade phases. Provider-backed fresh grading can vary because it asks the judge again; repeat `grade` without `--rerun` to reuse the current judgment. It does not remember selector or sample flags from a previous invocation.

## Job 7: Run anywhere — weave between local and hosted runners

    workbench eval --cloud
    workbench watch RUN_ID
    workbench improve --cloud
    workbench cancel RUN_ID
    workbench retry RUN_ID

`--cloud` is the hosted execution story: the same command, executed by the Workbench Cloud runner against the linked Cloud skill. Local and hosted launches share the same durable-run lifecycle: once launch readiness passes, Workbench persists a run snapshot plus queued/running job state before long work continues, and foreground CLI or browser callers attach to that run instead of owning the whole execution. Hosted eval and improve validate the local source/evidence plan and selected hosted provider auth first; when hosted plan access is knowable from the linked or derived target, that plan check also happens before any temporary handle, auto-link, sync, or scheduling. `improve --cloud` reports local target and evidence issues before hosted plan checks, auto-linking, or hosted progress. Hosted retry validates the stored operation plan first. Once the local plan, selected hosted provider auth, and knowable hosted target are valid, the CLI creates a local watchable live handle and prints progress with the exact `workbench watch RUN_ID` resume command before Cloud auto-link, sync, resolve, and schedule steps that may take time. Before Cloud accepts the run id, progress is labeled as preparing the Workbench Cloud run; JSON progress uses planning or syncing phase without reporting the run as queued, and queued plus hosted-worker wording is reserved for accepted Cloud run snapshots. That handle is visible to read-only local inspection but is not uploaded as an object-pack run during sync; if auto-link, sync, resolving, or scheduling fails before Cloud accepts the run after a temporary handle exists, Workbench clears that temporary handle and returns the setup error without durable run evidence. Before Cloud accepts the run id, `workbench watch RUN_ID` follows the local live handle and `workbench cancel RUN_ID` cancels that handle locally; the original hosted command stops promptly before scheduling, even when pre-schedule sync is still running. Intentional cancel or detach during that window does not overwrite remote sync health with an abort error. Local objects then sync up, Cloud accepts that same run id and derives the runtime packet from its stored project state, and the CLI replaces the local live handle with the authoritative Cloud run snapshot. The wait loop observes hosted inspection snapshot envelopes and state notices, deriving progress from the same `workbench.run.v1` snapshot facts the web UI uses; terminal evidence sync is reported as an explicit progress phase before local state updates when the run finishes. A promoted hosted improve also reconciles the same Cloud remote after switching local source, so `status` and `sync cloud --dry-run` agree when the command exits. Hosted runner capacity keeps five warm hosts for the common 20-sample eval loop and scales out in five-host increments for larger queues. Long-running run, grade, eval, improve, and retry commands, write sparse concrete progress to stderr: phase, planned/completed/scored work, partial score only while clearly labeled partial, failures and cancellations, active job, evidence count, reported usage cost, and elapsed time. Workbench does not show ETA. Stdout remains one parseable JSON document for `--json`, containing one run snapshot; once a durable run exists, stderr progress JSON Lines are newer `workbench.run.v1` snapshots for that run, and pre-run checks do not mint a second JSON progress schema. Terminal failed or canceled `workbench.run.v1` snapshots and terminal `watch` output omit self-referential `next: workbench show RUN_ID` hints. The first Ctrl-C detaches promptly with exit 130, leaves the local worker or hosted runner active, aborts the attached Cloud wait, and prints `next: workbench watch RUN_ID`. `workbench watch RUN_ID` is the explicit resume command for a known run, exits `0` after successfully reporting any terminal snapshot, and syncs terminal hosted evidence before returning when needed; scripts read `run.status` for succeeded/failed/canceled semantics. Succeeded eval watch/retry next commands preserve non-default version or agent selectors, so the printed `results` command inspects the evidence that was just watched or retried. `workbench cancel RUN_ID` requests cancellation and returns with a terminal-aware next command; canceling an already terminal run returns `run_terminal` with `workbench show RUN_ID`. `workbench retry RUN_ID` starts a new whole-run attempt from the selected run's stored operation plan, creates the same local watchable handle before hosted repair work, and for hosted runs syncs or auto-links the Cloud skill before resolving and scheduling the retry, so pre-accept canceled runs do not require a manual publish. Read commands inspect local committed Workbench state only; Cloud-owned hosted evidence imported by watch, hosted waits, or explicit sync is tracked as Cloud-owned and does not by itself make `status` report sync `local_changes`; `workbench sync cloud` remains explicit object-exchange repair and portability plumbing for local source or object changes. One-time setup: `workbench login` must be active, provider auth for the selected hosted agent must be captured, and the linked Cloud skill must be organization-owned under an active Team or Enterprise plan. If no Cloud skill is linked yet, the first `eval --cloud` or evidence-ready `improve --cloud` auto-links an unpublished Cloud skill project in the available namespace; users who need hosted compute should create or choose an organization-backed project before running the hosted happy path. Publishing installable source remains a separate explicit `workbench publish` action.

Hosted eval is still the hosted happy path: Cloud queues execute jobs and then grade jobs with explicit subject dependencies, so hosted grading sees the runner output, workspace, and traces without mutating the runner artifacts. Local `workbench run` and `workbench grade` remain the phase-specific output-only and judgment-only commands; they use the same durable-run progress and inspection model when they launch work.

Progress summaries include remaining selected work while a run is not terminal, for example `work 4/10 complete, remaining 6`, alongside the active case/sample/job. Workbench still does not guess ETA.

## Job 8: Make it better from evidence

    workbench improve
    workbench improve --cloud
    workbench improve --dry-run --cloud

`improve` requires graded below-perfect, failed, or reviewed eval evidence, edits the selected mutable package source outside `.workbench/**` with one explicitly selected improvement-capable agent (same plural `--versions`/`--agents` grammar as `run`, `grade`, and `eval`; values must resolve to exactly one entry each, and the error names the exact corrected command when they do not), records the candidate version plus proof execute and proof grade jobs, and switches only when the proof run succeeds and beats the incumbent. The candidate may update `SKILL.md`, scripts, references, assets, or other package support files; ordinary improve reads `.workbench` evidence and controls but does not rewrite `.workbench/**`. `improve --dry-run` resolves the selected version, agent, evidence, incumbent, proof eval plan, location, auth plus local Docker sandbox readiness, and package write scope for the same edited current source a real improve would reconcile, without editing source, scheduling proof work, syncing Cloud, auto-linking, or writing Workbench object state. Missing auth or Docker readiness is reported as blocked readiness with the setup command while preserving the preview; if hosted improve also needs Workbench Cloud auth, the remediation begins with `workbench login`. The selected agent is both the improver and proof eval agent, so it appears in `results` with the same status and score semantics as any other run. Hosted `improve --cloud` follows that same switch contract after terminal Cloud evidence syncs back, then reconciles the Cloud remote once more when it switches local source. Perfect eval runs are not improvement evidence. Once the selected proof agent has a perfect current comparable eval for the same eval definition, older below-perfect traces stop making `improve` ready. Ungraded execution-only output, unscored runtime failures, and auth failures are not improvement evidence; historical scored smoke-labeled failures are still evidence. If the current eval definition has not been run yet, improve remediation is `workbench eval`; if current execution exists but current grading does not, improve remediation is `workbench grade`; if current evidence is perfect-only, remediation is `workbench case draft CASE_ID` for the next unused headless case instead of an unconditional rerun command. When a one-sample proof run switches the current source, the next command is a higher-sample rerun before publish. Once actionable evidence exists, if the selected eval agent cannot improve, `improve --dry-run` returns a blocked readiness envelope instead of exiting usage, and both dry-run and real improve suggest the first staged setup command. JSON `subject.setupCommands` carries provider auth, improver rerun, and improve; hosted dry-run reports local improve-agent ineligibility before Cloud target checks. One-time setup for the taught bare Codex command is `codex login --device-auth` if `~/.codex/auth.json` is missing, then `workbench login codex --method oauth`, then `workbench agent add default --adapter codex --model gpt-5.4-mini --with auth=default`. The Claude equivalent is `claude setup-token` in an interactive shell, browser authorization, `CLAUDE_CODE_OAUTH_TOKEN=... workbench login claude --method oauth`, then `workbench agent add default --adapter claude --model sonnet --with auth=default`.

## Job 9: Decide which agent or version to ship

    workbench results
    workbench results --agents all
    workbench results --versions all
    workbench versions

`results` renders one scorecard for one eval definition across selected versions and agents, including the `source: none` no-skill row and failed runs as visible failure evidence. It is pure inspection over committed local Workbench state: it does not reconcile edited files into a source version, create derived eval or skill-bundle objects, or rewrite refs. Human output is evidence-first: selected rows with no recorded run stay out of the table instead of printing `not-run` noise, while JSON keeps the full valid selected matrix for automation. `workbench results --versions all` keeps historical source snapshots in view; `workbench results --versions current` narrows to the current source snapshot, and unambiguous version-id prefixes select that exact result row. If the current selected version has no recorded evidence, human output says that explicitly and prints `next: workbench eval` even when historical evidence is visible in the same table. Execution-only evidence from `workbench run` is visible as run/job evidence but remains ungraded in scorecards until `workbench grade` or `workbench eval` creates grade result items. Recorded run evidence remains comparable even if an unrelated historical source manifest is no longer parseable. A single matrix eval run can populate multiple result cells through its job-backed measurements. When multiple runs or measurements match a cell, Workbench prefers terminal evidence with the most case/sample coverage and uses recency only as a tie-breaker; canceled partial evals keep canceled status and sample coverage but show `n/a` quality rather than a completed score. Human latency is average per sample for multi-sample runs. Version and run ids display as short unique prefixes everywhere and any unambiguous prefix is accepted wherever a REF is expected. `workbench versions` lists committed immutable source snapshots only; it does not reconcile edited files into a new version. The web `Evaluation > Results` surface is the browser counterpart over the same snapshot.

## Job 10: Understand what happened

    workbench                     # bare invocation = status + the next useful command
    workbench log                 # one reverse-chronological timeline of versions and runs
    workbench versions            # compact immutable source version list
    workbench show r4f2           # any object id: run, job, trace, version, artifact, session
    workbench show job_abc
    workbench watch r4f2      # follow one active or hosted run
    workbench open                # browser UI over the same snapshot

Three universal read verbs cover inspection: `status` (where am I: worktree, active runs, publication, sync health, auth), `log` (what happened, filterable with `--runs` or `--versions`), and `show` (give me the thing: interpreted run/job evidence, file listings for file-backed objects, or one file via `REF:PATH`). `versions` lists committed immutable source versions only and does not reconcile edited files; launch and publish paths reconcile current source when they need it, and default `diff` reconciles current source before computing its implicit current-vs-parent range. `run` is output-only execution for selected cases; known-run lifecycle operations are top-level `watch`, `cancel`, and `retry`. Use `workbench show RUN_ID` first for terminal multi-sample runs; its file list prints copy-paste complete commands such as `workbench show RUN_ID:cases/.../output/result.json`. If shorthand like `workbench show RUN_ID:result.json` matches multiple jobs, the error keeps failing as ambiguous but lists exact `workbench show RUN_ID:cases/.../result.json` candidates. Then open a specific listed job stream such as `workbench show JOB_ID:stderr.log` when that file is present. Use `workbench watch RUN_ID` for active or detached runs. `show RUN_ID` uses the same progress snapshot and evidence count as `status` and `watch`; failed or canceled run pages do not point back to themselves as the next command. Public `show` job sample labels are one-based like live progress in both human and JSON command output. `show RUN_ID` also previews public provider evidence when available: model output, evidence-backed provider session refs, rubric scores, and rubric rationales. Provider session refs printed by Workbench evidence resolve through `show`, and native local provider sessions resolve when the local provider files exist. `workbench open` serves the same snapshot envelope as a foreground server, prints the bound URL plus a `Press Ctrl-C to stop` hint, and exits `0` after that intentional stop; browser freshness comes from snapshot envelopes plus live state notices. The browser starts on `Files`, keeps scorecards under `Evaluation > Results`, authored cases under `Evaluation > Cases`, and active/completed run history under `Runs`. Full-access local browser pages start run/grade/eval/improve through the shared operation endpoint, which returns a `workbench.run.v1` snapshot after durable run state exists while the private local worker continues; hosted full-access pages expose the hosted operation kinds Cloud can start, currently eval/improve. Source-only pages expose acquisition actions only. All reads use local committed Workbench state and work without the project write lock, so they remain usable while run, grade, eval, or improve is running. `status` can report active runs and sync `local_changes` without contacting Cloud; if that sync repair is not the primary workflow next step, status still exposes `syncNext`/`sync next: workbench sync REMOTE --dry-run`. When the linked Cloud remote cannot be reconciled because the CLI is logged out, sync status is `auth_required` and the next command is `workbench login`. Network freshness is explicit through `workbench watch RUN_ID`, `workbench sync cloud`, `publish`, `install`, and hosted command scheduling.

Every job is inspectable through the same path. `workbench show JOB_ID` renders the job role, status, adapter, context, dependencies, generic result items, artifacts, and traces, so execute, grade, and improve jobs do not need separate evidence commands.

## Ergonomic invariants

These properties hold across every job and are checked when any of them changes:

- Zero flags on the happy path: each job's steady state needs no flags except `--cloud` (destination) and `--public`/`--team` (audience).
- One handle: `OWNER/SKILL` everywhere, with `OWNER/SKILL@VERSION` for exact still-published versions; URLs accepted, never required.
- One evaluation selector grammar: `--versions`/`--agents`, plural, manifest defaults, on every run, grade, eval, improve, or results command that selects measured source versions or runtime agents. Skill accessibility uses `--target codex|claude` and `--scope folder|global` because it selects coding-agent products and access roots, not eval agents.
- One install/list split: `workbench install SOURCE` mutates agent-visible skill roots, and `workbench skills` reads accessible skill inventory. Bare `workbench install` is a usage error, not a list shortcut.
- Agent-friendly aliases: required positional inputs also accept flags for automation, including `new --dest`, `clone --source --dest`, `install --source`, `publish|unpublish|switch --version`, `show --ref`, `diff --range`, `sync --remote`, `case draft --id`, `agent add|rm --name`, and `watch|cancel|retry --run`.
- Install targets are hidden until needed: `skills` scans broadly by default because it is read-only; `install` writes one detected folder target by default because it mutates files. `--target`, `--scope`, and `--dir` are the exposed target controls for Codex and Claude.
- Source is package-wide: Workbench versions, evaluates, improves, and publishes the whole agent skill package, not only `SKILL.md`. Installed packages exclude `.workbench`; editable Workbench source comes from `workbench clone OWNER/SKILL[@VERSION]|URL DIR`.
- One durable run per accepted launch: each accepted `run`, `grade`, `eval`, `improve`, or `retry` command creates one durable run id; pre-accept hosted setup failures may expose a temporary correlation id only under `subject.correlationRunId`. Matrix expansion belongs to jobs and run measurements, so `show`, `watch`, `cancel`, and `retry` all operate on the durable id the launch returned.
- The tool teaches itself: human output ends with at most one `next:` line, JSON envelopes carry at most one `next`, and the suggestion follows the causal chain (auth before link before sync before publish; authoring before publishing); bare `workbench` always tells a new user what to do next.
- Error remediations are command-shaped: when human output renders `next:`, the value is the command to run, and JSON `remediation` carries the same command without a prose wrapper.
- Ten taught lifecycle commands (`new`, `init`, `run`, `grade`, `eval`, `improve`, `results`, `publish`, `skills`, `install`); `clone` is source acquisition, `versions` is version inspection, `unpublish` is publication administration for prior exact versions, `watch`/`cancel`/`retry` are known-run lifecycle operations, and everything else is inspection or plumbing behind `workbench help --all`.
- Location-clear network: a run is the same object whether it executed locally or hosted, but ordinary reads never hide network synchronization. Hosted waits sync terminal evidence once; detached or stale hosted state is refreshed by the explicit known-run command `workbench watch RUN_ID`, while `workbench sync cloud` remains object-exchange repair for local source or local-only object changes.
- Scriptable commands support `--json` with a schema-tagged envelope, so agents complete the same jobs with the same sequences. Non-launch JSON commands keep human progress prose off stderr. `workbench open` is browser-server only; agents use `log`, `show REF`, `show REF:PATH`, and `watch RUN_ID` for non-browser inspection and operation.
- Dirty source is visible before reconciliation: `workbench status --json` reports `worktree.sourceState: "would_create"` and `worktree.wouldCreateVersionId`, human status prints the would-create version, and the causal next command is `workbench eval` once cases exist, preserving a prior non-default eval agent selector when that is the runnable proof path.
- Long-running JSON commands keep stdout to one schema-tagged JSON document and, after a durable run id exists, write `workbench.run.v1` snapshot JSON Lines to stderr; pre-accept hosted setup failures may carry a temporary correlation id only under `subject.correlationRunId`.
- Short ids: object ids display as short unique prefixes, and any unambiguous prefix resolves wherever a REF is accepted; full ids live in JSON.
- Summary-first JSON: envelopes embed file manifests, never file contents; `show REF:PATH` is the only content read.
- One evidence tree: every run/job evidence file has one canonical user-facing path; `show` renders runnable `workbench show REF:PATH` commands for listed files. Internal `.workbench/` runtime files and raw trace metadata files are not addressable run/job evidence.
- `--dry-run` never writes: a dry run that mutates state is a defect, everywhere.
- Errors teach too: selector errors enumerate the configured values, and remote errors never embed raw response bodies.
